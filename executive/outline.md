# Outline of executive and cortex structure

## Background

This will the controller for a small mobile droid interacting with a domestic environment. The physical capabilities of the droid will evolve over time. Currently it comprises:

- a mobile rover platform with mercanum wheels above to move forward/back, rotate on the spot but also slide sideways or diagonally
- a camera able to deliver video or still capture at low or HD resolution
- sensors for absolute heading and distance to obstacles in front (and at 30 degrees either side of the front)
- an onboard Raspberry Pi running a web server that can be used to obtain camera and sensor data and to send movement instructions

The web server code is in ../pi-master/camera_server.py

## Goal for this development

Build an agent layer (the "executive") that takes prompts form the user (initially typed into the terminal) and maps out a plan for what the rover should do.

Build a lower layer (the "cortex") which executes the plan but monitors if the rover is getting too close to an obstacle or if the plan is complete. In such cases it should stop the rover and ask the executive what to do next.

The LLMs used by the executive will be running locally in llama.cpp in this machine, the details of that are out of scope here.

There will be a thinking model on one localhost port and a VLM model on another port.

## Initial outline

### Dialog handler

- A module that takes text input from the terminal.
- If the text is "stop" it tells the context the stop the rover.
- Otherwise it should pass the prompt the exective along with a summary of the current state so that the executive can decide whether to change the plan or simply repond to the prompt without changing the plan.
- Outputs from the executive agent should be shown back the user

### An Executive Agent

- This should use an LLM on a localhost port (with OpenAI compatible completions API).
- It should be implemented using the pydantic.ai framework
- It should take current state, event updates from the cortext and prompts from the user and either:
   - send a text response to the user without further need for tool use
   - use tool calls to help answer the question but without changing the plan
   - update the plan the cortext should be following

### A cortex module

- This should maintain a state object for the current plan and drive the rover via the camera_server web interface to execute the plan
- Check if there an obstacle closer than 10cm and if so stop the rover and inform the executive
- Provide a call that the dialog handler can invoke directly if the users says "stop"
- the cortex should update the rover state information (see below) once every 200ms

### State

The modules should coordinate via two groups of state information.

#### High level state

- rover mode (standby, acting)
- current goal as set by the user prompts
- high level plan for how to achieve this generated by the executive LLM

#### Rover state

- heading
- isMoving
- distanceToObstacle
- current camera image
- list of visible objects and their heading

### Tools to provide to the executive

- check if an object of named time is visible
- turn to the object, if is visible
- move in a direction for a distance
- a sequence of movment actions
- get the current heading
- return the distance to obstacle in front
